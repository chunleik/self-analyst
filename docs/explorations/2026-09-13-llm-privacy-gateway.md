# 可选 LLM 隐私网关与多语言实体识别探索

记录日期：2026-09-13。资料核查范围：2026-09-12 至 2026-09-13。

状态：探索记录，尚未实施或部署。本文保存讨论方向、源码调查和后续验证建议，不是现行行为契约，也不表示其中的建议已经成为产品配置。

现行行为仍以 [OpenSpec 主规格](../../openspec/specs/) 和 [系统架构](../architecture.md) 为准。本次文档保存由 OpenSpec change `document-llm-privacy-gateway-exploration` 追溯；该 change 的完成或归档仅表示文档已保存，不表示网关功能完成。

## 1. 背景与当前方向

目标是在上下文发送给外部大模型前，识别并处理个人信息、凭据及业务敏感信息，同时尽量保留活动分析、历史回顾、工具查询和摘要的可用性。

讨论最初评估了“Presidio 独立服务＋中文实体识别配置＋业务自定义规则”。后续用户提出以 **LiteLLM + Presidio 作为可选配置，并让实体识别支持国际化**，因此当前优先探索这一组合。

建议的总体方向是：

- LiteLLM 提供统一模型网关，在发送上游请求前执行保护策略。
- Presidio 在本机或可信内网运行，负责规则和模型识别，以及所支持的脱敏操作。
- 通过语言与地区配置、统一实体目录、业务对象别名和独立策略扩展检测能力。
- 借鉴本体的分类与语义对齐思想，初期不引入完整 RDF／OWL 系统或推理引擎。
- 先验证出站覆盖、识别效果和任务可用性，再决定正式接入与桌面分发方式。

这条路线可行，但模型网关、多语言参数与实体分类本身都不能保证敏感内容没有漏检。

## 2. 当前调查覆盖与证据边界

已经完成官方文档及部分上游源码核查，并调查 SelfAnalyst 的模型构造、动态上下文、plain 调用、压缩模型包装和 embedding 客户端。没有安装 Presidio、spaCy 中文模型或 LiteLLM，没有对真实业务数据运行脱敏，也没有测量延迟、内存或端到端检出率。

调查期间用 Python 标准库做过两个小型语义演示：连续中文下的单词边界匹配，以及 Unicode 码点与 UTF-16 下标差异。它们帮助解释接入风险，不属于 Presidio 包级回归测试或模型评测。

本文引用的上游默认配置、API 和源代码均以核查时可见版本为依据，`main` 分支内容可能变化。后续验证应固定 LiteLLM、Presidio、模型与规则版本，并再次确认许可证、开源功能范围及实际接口行为。

## 3. 候选部署和可选配置

### 3.1 责任边界

建议的受保护路径如下。图中 LiteLLM 和 Presidio 都位于本机或可信内网；外部模型只接收脱敏后的请求。

```text
SelfAnalyst --> LiteLLM --> External LLM
                  |
                  v
               Presidio
                  |
                  v
          Rules / NER / Mapping
```

LiteLLM 调用 Presidio 并取得结果后，再决定替换或阻断上游请求。这个网关本身能够接触原文；把网关放到不可信外部服务再做脱敏，不能满足原文留在可信边界内的目标。

作为对照方案，Java 也可以直接调用 Presidio 服务再请求模型。它便于在应用中控制字段与工具语义，但需要自己统一多个模型出口。网关方案则需要额外服务运维，并核查各 API、消息内容块与调用选项是否真正执行了保护。

### 3.2 建议的用户可见行为

以下是候选行为，不是当前已有配置键或最终 UI 设计：

| 设置或状态 | 建议语义 |
|---|---|
| 是否启用隐私网关 | 默认关闭；关闭时沿用现有连接方式，不自动启动或连接隐私服务 |
| 网关连接 | 使用单独的网关地址和凭据；上游模型凭据由部署侧管理 |
| 保护策略 | 选择经验证的策略版本，不在普通模型表单里暴露完整识别器实现 |
| 检测语言与地区 | 展示已配置且已验证的能力；与界面语言分开 |
| 故障处理 | 启用后遇到检测不可用或不完整时暂停受保护外发，不自动绕过网关直连 |
| 诊断 | 区分网关连通、语言模型就绪、策略生效以及各出站路径验证情况 |

部署侧应确保受保护凭据或路由执行指定策略，避免只依赖客户端逐次声明要使用 guardrail。具体强制绑定机制、请求覆盖参数和绕过条件需要在选定 LiteLLM 版本上验证。

LiteLLM 的 Presidio 集成支持调用前处理、掩码与阻断等能力；这里需要使用调用前生效的策略。`logging_only` 只净化日志，不能替代实际请求脱敏。[LiteLLM 集成说明](https://docs.litellm.ai/docs/proxy/guardrails/pii_masking_v2)

### 3.3 部署成本

建议 PoC 先使用独立常驻服务，预装模型并预热，不把下载模型放到首个用户请求中。第一阶段可以由开发或部署环境管理服务；是否随桌面安装包分发，留待验证后决定。

当前 Windows 发布包主要包含桌面 EXE、后端 JAR 和 JRE。若内置隐私服务，会增加 Python 环境、模型文件、端口认证、启动就绪、故障恢复、关闭和升级工作。不建议在没有验证用户环境前，把 Docker 当作所有桌面用户的必需依赖。[当前发布结构](../architecture.md)

## 4. 实体识别的国际化

### 4.1 四个独立维度

| 维度 | 职责 | 示例与约束 |
|---|---|---|
| 界面语言 | 标签、设置、提示和诊断文案 | 沿用 `app.language`；英文界面也可能处理中文标题 |
| 内容语言 | 选择 NLP 模型和语言相关上下文词 | `zh`、`en`；同一请求可能同时出现多种语言 |
| 国家／地区 | 选择号码、证件及地区格式规则 | 中文内容也可能包含其他国家号码，不能由 `zh` 唯一决定 |
| 实体类型 ID | 策略与识别结果的稳定语义接口 | `PERSON`、`ORGANIZATION`、候选业务类型 `INTERNAL_PROJECT` |

当前项目国际化控制界面、固定提示词和回复语言，不改变用户数据语义。检测语言不应简单绑定界面语言；用户原文也不应为了检测而先发送给外部翻译服务。[国际化主规格](../../openspec/specs/internationalization/spec.md)

LiteLLM 文档提供默认 `presidio_language` 和请求级 `guardrail_config.language`，后者优先；未配置时默认为英文。Presidio 的多语言能力还要求对应 NLP 模型、识别器及上下文词已经就绪。这两个参数不等价于自动语言检测或完整混合语言支持。[LiteLLM 语言设置](https://docs.litellm.ai/docs/proxy/guardrails/pii_masking_v2)、[Presidio 多语言说明](https://github.com/data-privacy-stack/presidio/blob/main/docs/analyzer/languages.md)

### 4.2 混合语言与能力扩展

候选策略是：格式规则覆盖配置的地区，NER 按片段语言路由；短标题或语言判断不确定时，对配置的少量语言模型进行扫描并合并结果。多模型结果需要处理同一片段的重叠、冲突、类型映射和优先级。这属于需要验证的扩展逻辑，不能当作现成集成承诺。

初期以项目实际使用的中文和英文建立测试基线，设计上允许追加其他语言。新增语言不仅需要翻译显示标签，还应提供模型、识别器配置、地区规则、正反例和质量报告。界面文案可以回退到英文；检测器缺失则应报告能力不足，不能沿用文案回退逻辑并宣称检测完成。

## 5. 中文能力与默认配置风险

Presidio 可以接入 spaCy、Stanza、transformers 等 NLP 引擎，并允许自定义识别器。中文适配需要同时处理模型配置与识别规则。[模型扩展说明](https://github.com/data-privacy-stack/presidio/blob/main/docs/analyzer/customizing_nlp_models.md)

| 核查发现 | 对方案的影响 |
|---|---|
| 默认 NLP 配置使用英文模型 | 显式安装和注册中文模型，不只传入 `language=zh` |
| 当前 `PhoneRecognizer` 默认区域不包含 `CN` | 为国内号码配置地区与中文上下文词，并验证中英混排场景 |
| 当前默认配置忽略 `ORGANIZATION` | 若要保护客户机构，需启用机构实体，并用业务规则控制误报 |
| 默认 `deny_list` 使用非单词字符边界 | 连续中文中的内部项目名可能漏匹配，需要中文词典或子串匹配逻辑 |
| spaCy 适配器默认给实体使用配置分数 | 不能把返回的分数直接解释为经过校准的真实正确概率 |
| 正则识别器捕获超时后跳过该规则 | HTTP 成功不一定表示所有检测完成，严格模式需能识别不完整扫描 |

对应来源：[默认 NLP 配置](https://github.com/data-privacy-stack/presidio/blob/main/presidio-analyzer/presidio_analyzer/conf/default.yaml)、[手机号识别器](https://github.com/data-privacy-stack/presidio/blob/main/presidio-analyzer/presidio_analyzer/predefined_recognizers/generic/phone_recognizer.py)、[词典边界和超时处理](https://github.com/data-privacy-stack/presidio/blob/main/presidio-analyzer/presidio_analyzer/pattern_recognizer.py)、[spaCy 适配器分数](https://github.com/data-privacy-stack/presidio/blob/main/presidio-analyzer/presidio_analyzer/nlp_engine/spacy_nlp_engine.py)。

spaCy 3.8.0 官方通用实体评测中，`zh_core_web_sm` 的总体召回率约 65.0%，`zh_core_web_trf` 约 74.0%。这些数值不是本项目的敏感数据检出率，也不是模型速度数据；它们说明需要用目标业务语料评估，不能仅以模型支持中文作为验收依据。[小模型评测](https://github.com/explosion/spacy-models/blob/master/meta/zh_core_web_sm-3.8.0.json)、[Transformer 模型评测](https://github.com/explosion/spacy-models/blob/master/meta/zh_core_web_trf-3.8.0.json)

建议先对比“规则”“规则＋中文小模型”“规则＋Transformer 模型”，以检出、误报、延迟和任务质量决定选型。

## 6. 业务规则和处理策略

### 6.1 数据分类

| 数据 | 候选检测方法 | 候选处理方式 |
|---|---|---|
| 密码、API Key、访问令牌 | 格式、字段名与上下文规则 | 删除或阻断；不自动还原 |
| 手机号、邮箱、证件号 | 格式规则与适用的校验逻辑 | 完整替换，而非只隐藏部分字符 |
| 姓名、客户名、内部项目名 | 中文／英文 NER＋已知业务词典 | 稳定代号替换，按场景决定是否还原 |
| 本地路径、内部域名、带令牌 URL | 路径／URL 解析与业务规则 | 移除敏感部分，保留所需文件类型或公开技术信息 |
| 时间、时长、应用名、统计值 | 按字段和业务用途配置 | 保留任务需要的分析信息，避免一律遮蔽 |
| 未公开计划、合同事实、间接身份线索 | 业务标记、上下文规则或后续语义检测 | 需独立评估，不能假定通用 NER 已覆盖 |

格式校验失败不应自动成为放行依据：带错字的证件号、变形凭据和短标题仍可能敏感，需要通过正反例明确策略。

### 6.2 识别、归一与策略分离

识别器回答“这段内容是什么”，策略回答“在什么用途、发送给什么目的地时应如何处理”。`ORGANIZATION` 不必始终遮蔽，但登记为内部客户的对象可以采用更严格策略。类型、业务角色、敏感级别与处理动作应分别建模。

对象别名归一需要有依据。类型标签 `PER` 与 `PERSON` 可以映射到统一类型；“张三”和“Zhang San”是否属于同一对象，不能仅凭翻译或拼音自动认定。词典应记录来源、别名和更新时间，并验证简称歧义及重叠词。

### 6.3 代号、还原与状态

候选例子：同一客户在历史、工具结果与本轮消息中统一为 `<CLIENT_1>`；另一客户使用 `<CLIENT_2>`，以保留关系。示例代号形状不是已存在的协议。

Presidio 默认 `replace` 通常生成实体类型标签，例如 `<PERSON>`；完整会话映射和可靠还原不能由此推导。LiteLLM 的 `output_parse_pii` 提供还原相关能力，但会话稳定性、并发隔离、流式片段和工具参数行为需要按版本验证。[Presidio 算子](https://github.com/data-privacy-stack/presidio/blob/main/docs/anonymizer/index.md)、[LiteLLM 输出处理](https://docs.litellm.ai/docs/proxy/guardrails/pii_masking_v2)

需要进一步设计的状态约束包括：

- 原始本地会话与事实保持原值，只为外发构造副本。
- 映射按会话或任务隔离，明确跨轮、跨进程重启和删除会话时的生命周期。
- 对原文已含类似代号的情况避免碰撞；不把未知或其他会话的代号恢复成真实值。
- 滚动摘要若保存代号，须有相应持久映射或还原策略，避免后续失去引用关系。
- 流式还原处理跨片段代号；结构化消息保留合法 JSON、工具名、字段名与调用 ID。
- 本地工具可能需要恢复路径；外部搜索或 MCP 参数必须重新经过出站策略，不能无条件恢复原值。

若应用直接消费 Presidio 字符位置，需正确转换 Python Unicode 码点与 Java UTF-16 下标；emoji 等字符会使两者不同。让识别和替换在同一 Python 服务完成可减少这类跨语言风险。

## 7. 是否需要本体

### 7.1 目前需要的建模能力

| 层次 | 解决的问题 | 初期承载方式 |
|---|---|---|
| 实体分类 | 人员、组织、项目、标识符、凭据等概念及其定义 | 版本化类型目录 |
| 实体识别 | 从不同语言文本定位候选实体 | Presidio 识别器与 NLP 模型 |
| 对象归一 | 已知对象的全称、简称和跨语言别名 | 业务对象目录与显式映射 |
| 脱敏策略 | 类型／对象在用途和目的地中的处理方式 | 独立策略目录 |

统一目录建议至少记录：稳定类型 ID、定义、父类型、多语言标签、模型类型映射；业务对象另行记录对象 ID、别名及证据来源。策略目录记录用途、目的地、动作和是否允许还原，避免将这些字段固定成实体类型自身的唯一属性。

本体对概念组织和语义对齐有帮助，但不能直接提高实体识别模型的检出率。定义“客户属于组织”之后，系统仍需证据判断某个名称是否是客户。

### 7.2 初期采用轻量目录

可以参考 SKOS 的概念标识、多语言标签、上下位关系和映射思想，用 YAML／JSON 管理即可，不要求立刻采用 RDF 存储。类型层次如何参与策略继承仍应由应用明确，不能假定引入 SKOS 就自动获得业务推理。[W3C SKOS 指南](https://www.w3.org/TR/skos-primer/)

语言与地区能力也建议独立登记模型、规则、支持范围及验证版本。显示名称的国际化与对象身份归一分开维护。

### 7.3 何时再评估关系推理

若后续需要表达“项目属于保密客户，所以关联联系人、内部代号与未公开合同事实都应继承保护策略”，才出现较强的关系建模与推导需求。

届时先比较普通关系表和规则引擎是否足够。如果确有跨系统语义互操作、复杂分类推理或一致性检查需求，再评估 RDF／OWL。关系来源及推导结果仍需可追溯；模型猜测的关系不能直接成为对象身份或放行依据。[W3C OWL 2 指南](https://www.w3.org/TR/owl2-primer/)

## 8. 与 SelfAnalyst 的接入关系

### 8.1 出站覆盖清单

| 路径 | 已核查的本地入口或契约 | 后续验证重点 |
|---|---|---|
| Agent 聊天与工具后续推理 | [SelfAnalystAgent](../../self-analyst-app/src/main/java/com/selfanalyst/agent/SelfAnalystAgent.java)、[上下文中间件](../../self-analyst-app/src/main/java/com/selfanalyst/agent/ConversationContextMiddleware.java)、[动态记忆中间件](../../self-analyst-app/src/main/java/com/selfanalyst/agent/DynamicMemoryContextMiddleware.java) | 组装后的 system、历史、桌面上下文、记忆及工具结果均经过保护 |
| Plain、Wiki 及其他文本生成 | `SelfAnalystAgent.completePlain`、`PlainTask`、`wikiLLMClient` | 独立调用不能绕过聊天以外的保护入口；继续梳理所有调用方 |
| 长会话压缩 | [UsageMeteredModel](../../self-analyst-app/src/main/java/com/selfanalyst/agent/UsageMeteredModel.java)、[压缩规格](../../openspec/specs/agent-context-compaction/spec.md) | 压缩调用、保存后的摘要及后续引用保持一致 |
| Embedding | [OpenAiCompatibleEmbeddingClient](../../self-analyst-wiki/src/main/java/com/selfanalyst/wiki/semantic/OpenAiCompatibleEmbeddingClient.java)、[Wiki 规格](../../openspec/specs/llm-wiki/spec.md) | 独立客户端、索引输入和查询输入都需验收 |
| 外部搜索／MCP | [联网搜索规格](../../openspec/specs/web-search/spec.md) | 当前工具参数出口独立存在，不能因聊天改走网关就宣称已保护 |

当前 plain runtime 保留具体的 `OpenAIChatModel` 类型，聊天、plain 与压缩在 runtime 构造中建立。若选直接应用包装，需要调整对应抽象；若使用网关，仍需确保所有受保护调用实际采用对应端点、凭据与策略。

Embedding 需单独决定脱敏语义：索引与查询变换不一致会降低匹配效果，跨文档随机代号也可能破坏实体相关检索。不能未经测试就复用聊天的会话代号方案。模型与规则变化是否触发索引重建也是待决策项。

### 8.2 不扩大的数据边界

现行文件规格禁止读取和外发普通被监控文件正文，`.gitignore` 的受限读取仅用于本地过滤。文件元数据可以作为 Agent 工具结果进入配置的模型会话；引入脱敏不得将其误述为此前永不外发，也不能借此扩大正文采集权限。[文件元数据采集规格](../../openspec/specs/file-metadata-collection/spec.md)

现有标题采集、无截图／OCR／音频链路等边界继续有效。该探索不新增文件全文扫描、截图识别或数据库历史数据改写。

### 8.3 配置、日志与生命周期

后续正式设计需沿用已有单连接设置、凭据只写操作、配置发布及工作固定版本语义。切换到网关地址时应使用正确的目标凭据，不能把原供应商密钥自动发送到新目标。[模型设置规格](../../openspec/specs/llm-settings/spec.md)、[Agent 运行规格](../../openspec/specs/agent-runtime/spec.md)

脱敏前文本、映射表、模型请求体及异常回显不应进入未保护日志或观测系统。应以规则版本、实体计数、耗时和错误分类提供诊断。检测失败时保留本地采集与查询能力，受保护 LLM 任务按其原有本地回退或可重试失败路径处理。

## 9. 后续验证计划

以下均为建议的未来验证任务，本次未执行。

### 9.1 语料与识别质量

- 建立 300～500 条合成或人工标注样本，覆盖中英文及混合文本、短标题、路径、工具结果、URL、证件、凭据、机构和项目别名。
- 同时包含公开机构、普通数字、时间统计、相似词等负例，以及连续中文、全角字符、空格／换行变形和 emoji 等边界样本。
- 按实体类型和语言分别统计精确率、召回率及残留敏感片段，不只看一个总体分数。
- 用独立留出集评估，避免仅报告编写规则所用示例的命中情况。

### 9.2 出站与功能完整性

- 在模拟上游真正收到的请求体上验收，覆盖聊天、第二次推理、plain、压缩、embedding 和范围内的外部工具调用。
- 覆盖全部内容块及动态字段，保持协议结构、调用 ID 和工具配对合法。
- 测试服务不可用、模型缺失、未知语言、正则超时、扫描超长与部分扫描失败，确认不会自动发送原文。
- 测试并发会话、取消、流式片段、代号碰撞、别名歧义、模型切换与重启，检查还原隔离和引用一致性。
- 对比脱敏前后的摘要事实准确性、工具执行成功率、引用有效性与检索质量；本地时长等确定性指标保持一致。

### 9.3 性能与交付

以 2 千、1.2 万和 8 万字符等档位记录冷启动、预热后 p50／p95、峰值内存和并发开销。较长输入覆盖现有桌面上下文和事件工具结果量级；PoC 再据现有请求超时预算确定门槛。

检查离线安装、版本固定、模型就绪检测、失败恢复和 Windows 发版成本。实际验收阈值需在基线测量后确定；固定样本无泄漏不等价于对任意输入的保证。

## 10. 待决策问题

| 问题 | 需要的证据或讨论 |
|---|---|
| 第一阶段保护哪些出口 | 聊天、摘要、压缩、embedding、外部工具各自的价值与接入成本 |
| 第一阶段支持哪些语言／地区 | 实际数据分布、模型可用性和按语言的识别质量 |
| 网关由谁部署 | 开发自管、用户自管还是桌面内置；是否接受新增服务依赖 |
| 哪些信息必须保护 | 已知客户、内部项目、路径、身份信息和凭据的业务优先级 |
| 是否需要还原及跨轮持久化 | 摘要展示、工具执行、会话恢复及映射保存范围 |
| 如何处理未知语言与扫描不完整 | 可观察失败语义、允许的本地降级路径及 UI 提示 |
| 如何验证策略无法被绕过 | 固定版本的网关绑定方式、请求参数覆盖和实际出站记录 |
| Embedding 使用何种变换 | 检索质量、索引与查询一致性、规则升级后的索引处理 |
| 是否引入关系推理 | 是否已有超出实体目录和显式规则的真实业务需求 |

继续开发前应创建独立功能 change，确定上述会改变范围或行为的选择，再形成增量规格、设计和实施任务。本文可作为背景输入，不直接充当实施授权或验收规格。
