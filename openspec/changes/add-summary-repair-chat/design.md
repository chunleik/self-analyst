## Context

动机见 proposal.md。ClosedSummaryHistory 已能列出质量失败的叶周期，但缺少供修改操作使用的服务端目标身份。agent.js/events.js 的普通追问只注入上下文；chat.js 的多轮上下文能够绑定 session.contextSnapshot。WikiTools 当前只提供查询，不能保存修订。WikiEvidencePolicy.validateNarrative 对无支持的动作/成果断言抛出字段级错误；失败响应不作为成功检查点持久化，因此不能假定旧失败记录有可编辑原文。

WikiStore 当前接受 schema 4，修复需要原子保存摘要和来源审计；WikiGenerationStore 的周期预算独立持久化。实现前应核对所有实际发布入口，包括 worker 正常发布和检查点恢复，避免只有修复侧检查版本。此次跨 UI、会话、摘要生成和 SQLite 的行为需要设计文档。

## Goals / Non-Goals

**Goals:** 从失败小时旁进入可持续的对话修订，明确区分自动观察与用户自述，校验后提交并解除对应上级依赖。提供有界、可恢复且无误覆盖的发布过程。

**Non-Goals:** 不作为任意数据库编辑器，不修改原始事件或应用时长，不全局关闭质量校验，不清零额度，不批量重写已完成历史，不在开发验证时修复用户真实数据库。首期适用当前版本已结束且质量失败的记录；等待依赖的父条目指向实际可修复叶记录。

## Decisions

### 1. 入口与会话界面

失败状态行旁增加“对话修复”，保留普通追问。父条目下的每个失败依赖携带 entryId、层级、起止、时区和当前版本标识；服务端重查并决定是否可修复。按钮阻止冒泡到折叠切换，具备范围标签。不在概览正文中堆放修复参数。

使用现有会话页，创建或恢复 target + session 绑定的修复会话。上下文区显示“正在修复：10-12 16:00–17:00”、原因和来源；输入框预填“请帮我修订这个时段的摘要，并说明还需要我补充哪些事实。”，由用户发送。使用专用上下文类型 summary_repair，后端以保存的绑定判断权限，不把前端 context 当授权。

修订卡片放在对应回复之后，展示整体摘要、任务、引用来源和字段级问题。用户可以继续对话，也可直接编辑卡片。需要的用户陈述在卡片中逐项确认；有效后使用“保存修订”。持久化可编辑草稿并从服务端恢复，增强消息面与 fallback 使用同一渲染模型。会话绑定和每轮规范化上下文都包含目标，避免第二轮丢失入口信息。

替代方案：复用普通追问并解析“已修复”文字。舍弃，因为没有结构化校验结果、版本条件与可靠提交语义。

看板同时移除“未识别应用活动 X 分 X 秒”和“AFK 覆盖不足：部分时长未扣除非活跃时间，仅供估计”两类统计诊断。范围覆盖当前窗、历史条目和跨度条目的折叠/展开状态，以及证据区中重复的本地统计提示。移除后不留空容器、分隔线或空证据标签。优先按结构化诊断类型过滤展示；旧快照或既有 evidence 中的固定中英文文案在展示边界兼容过滤，不通过宽泛的 unknown/AFK 关键词删除真实技术主题。正常主题、应用统计、摘要失败/等待/额度原因及对话修复入口保留。

此处只改变看板展示，不修改 unknownActivitySeconds、sourceCoverage、coverage 或原始事件，不将估计值改标为精确值。生成器和诊断接口仍可消费真实覆盖信息。现行 SPEC-DSUM-STAT-001 要求展示这两类提示，本 change 以 MODIFIED 增量明确替换；用户主题中讨论 AFK 技术问题的文本不受隐藏规则影响。

### 2. 修复服务和模型入口

在 wiki 模块新增修复服务/存储接口，在 app 层新增受既有桌面会话和本机访问约束保护的 controller。建议 API 为 POST /desktop/summary-repairs 创建/恢复、GET /desktop/summary-repairs/{id} 读取、PUT .../draft 本地修改、POST .../validate 校验、POST .../commit 提交。所有变更请求使用服务端 session、repair、draftRevision 和目标版本；响应提供机器可读状态和可读提示，不返回任意异常正文。

修复会话的发送流程复用 canonical user/pending、取消、重试和 SSE 生命周期，但在后端路由到受目标周期预算约束的修复生成器。它只输出解释及候选结构，不暴露 Wiki 任意写入工具。普通 Agent 不拥有提交能力；模型结果和用户上下文一律不能直接触发 commit。

模型输入为有界当前允许事实、必要的成功子摘要、最近修复意见、有效草稿和安全错误码；采用既有隐私过滤。旧失败文案缺失时提示“原失败文本未保存，将依据现有记录重新整理”。所有修复模式模型请求在调用前经 WikiGenerationStore 周期与全局预算准入，防止借助普通聊天输出或隐藏的辅助调用绕过额度。重复 turn 复用结果、取消请求按既有真实消耗结算，不自动连环生成直到通过。

本地编辑/校验/保存不请求模型。额度耗尽且无候选时，先以允许事实提供引用选择和空的结构化编辑草稿，由用户输入有效摘要和任务；空草稿本身不能提交。UI 应区分模型不可用和本地修订仍可操作，不受普通 composer 禁用逻辑一并屏蔽。

### 3. 陈述来源与校验

自动事实仍按既有 observed/inferred 引用处理。用户主动输入的事实保存为有界 statement：目标、来源消息/直接输入、文本、版本、确认动作和时间。仅服务器从真实 user turn 或专用本地编辑请求建立 statement，模型只能建议纳入哪个用户陈述，不能设置 confirmed。

首期用确定性方法控制确认范围：对于包含成果/行为断言的 user_confirmed 任务，用户确认的任务描述必须与最终保存描述在脱敏和标准化后完全一致；普通模型改写使确认失效，需要重新确认。这样不需要调用另一个模型判断语义蕴含，也不会因为引用任意一条确认就豁免整段生成文本。用户可以直接编辑并确认该段，但不能把同一个确认扩散到其他任务。自动指标和应用引用仍独立校验，用户确认不赋予修改指标的权限。

整体摘要有独立断言校验：允许的用户确认成果必须逐项可对应；首期对包含这类成果的汇总采用本地组合已通过的任务描述，不接受模型新推断。父级输入保留 confirmed 来源与引用链，聚合按相同原则允许保留已确认内容，生成的新断言仍拒绝。混合来源不升级成纯观测；纯用户自述置信度至多 medium。更新生成协议/检查点版本，使旧模型或检查点不能误解新增类型。

修复候选运行与自动摘要一致的结构、引用、正文、主题限量、隐私及统计约束，增加明确的陈述来源分支，而非跳过 WikiEvidencePolicy。未经通过的模型响应不存原文；只存有界规范化草稿，标记 unvalidated/invalid/valid。不得作为成功检查点、查询结果或上级输入，日志仅记录字段与错误码。

替代方案：把所有修订标为人工确认并跳过校验。舍弃，因为模型生成的其他无依据断言会随之通过。

### 4. 原子存储与并发

Wiki schema 升至 5，增加目标 revision、repair drafts、statements、append-only repair revisions 和后续处理标记。摘要和修订/陈述来源在同一数据库事务内发布，commit 带幂等键与 draftRevision。草稿与审计按结构上限约束；不把聊天历史或完整模型输入复制进 Wiki。

prepare/validate 记录目标、允许事实、源子摘要和隐私/生成配置的指纹；commit 重新核对并校验。后台任务在开始读取时记录目标版本，最终提交及失败回写均使用版本条件；修复先发布后，旧请求不能将目标改回 FAILED 或覆盖摘要。后台先发布则人工保存返回 conflict，保留草稿，UI 读取最新结果。失败重试仅更新时间也应触发保守重载，不悄悄覆盖用户修订。

发布为 SUMMARIZED 后清除该目标的当前错误/下次重试并保留审计中的历史错误和累计消耗。可恢复的后续处理标记使快照失效、语义文档发现和父级重新检查在重启后继续；跨库操作不假设事务原子性。目标模型账本独立保留，不清零、不伪造未用额度。

首期只修复未完成条目，正常情况下不存在基于该条目的已完成祖先；仍须使用实际依赖关系核对，不重新生成无关历史。父级继续受其预算和其他依赖限制。语义索引按条目新内容/版本隔离旧结果。

### 5. 生命周期与隐私

草稿绑定会话并可在重启恢复；会话删除协调器清理未提交草稿。提交时在 Wiki 内独立保存必要的用户陈述、确认和修订内容，使删除聊天不破坏已保存证据。通过修订详情告知来源保存行为。保留当前采集边界，不读取文件正文，陈述经过相同脱敏和排除策略；原始用户消息按现有会话规则保存。

## Risks / Trade-offs

- 用户确认事实与自动观测混淆 → 独立引用命名空间、user_confirmed 类型、可见来源，父级保留引用链；不把用户自述等同独立验证。
- 确认文字更改后仍可提交 → 确认绑定规范化内容和草稿版本，任何修改使相关确认与校验失效。
- 后台回写与保存竞态 → 所有成功和失败发布采用相同 revision 条件，覆盖先后两种顺序与崩溃恢复测试。
- 旧错误无法定位具体句子 → 明示缺失，从当前允许事实开始新候选，不猜测被拒文本。
- 模型额度不足 → 不承诺对话一定恢复，提供不调用模型的本地草稿编辑/校验；父级额度不足时显示下一处真实阻塞。
- 新增用户证据扩大协议影响面 → 同步序列化、查询、隐私过滤、语义索引、上级聚合和兼容性检查，使用合成数据测试所有消费者。

## Migration Plan

实现后先用 schema 4 合成数据库验证事务迁移至 5、重复启动、异常恢复及旧数据可读，更新 RuntimeStorageCompatibility 与运行数据文档。迁移保留原记录，不自动触发历史重算。由于旧 WikiStore 拒绝版本大于 4，文档必须说明升级前备份及回退方式；不能直接降低 user_version。发布前完成离线 Java/Node 验证、界面截图、中英文文档与 OpenSpec 严格校验。主规格同步和归档仅在实施及验证完成后进行。
