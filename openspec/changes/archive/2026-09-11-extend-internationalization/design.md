## Context

动机见 proposal.md。现有 `Lang` 枚举、`LangResolver`、`Config.effectiveLanguage()` 提供中英文选择；`desktop-ui/i18n.js` 按 key 内嵌 zh/en，`utils.js` 把非 en 映射为 zh-CN，`state.js` 默认 zh。`init.js` 首次请求失败后仍沿默认语言启动，缺少明确恢复路径。Tauri `src-tauri/src/lib.rs` 的托盘和关于提示写死中文，部分 Java 桌面控制器直接构造中文错误。

主规格同时要求启动期语言不变和保存后仅刷新 WebView 即可切换，两者不能同时成立。本变更明确选择重启生效，替换该矛盾场景，不将其当成已实现行为。原生壳跨越后端未就绪和正常运行两个阶段，必须分别定义语言来源。

## Goals / Non-Goals

**Goals:**
- 在不修改业务调用点的前提下，通过集中注册项和资源扩展语言。
- 跨 Java、无框架 JavaScript 与 Rust 共享语言元数据，保持启动期语言一致和错误协议兼容。
- 以构建校验保障完整性，以运行时回退保障可用性。

**Non-Goals:**
- 不新增正式第三语言，不提供运行时翻译、资源下载、RTL、ICU 或即时整页切换。
- 不改写历史数据、用户输入、日志与中文项目文档，不更改安装器本身的语言系统。
- 不重构全部内部异常体系；转换边界限于应用拥有的用户可见桌面响应、确定性提示及原生对话框。

## Decisions

### 1. 集中注册语言，按语言分资源

在应用 classpath 的 `i18n/` 下维护单一语言清单，包含 code、显示名称、日期 Locale、资源标识，正式清单只注册 zh/en。Java 加载该清单，状态通道保留 `language` 并增量返回日期 Locale 与可选语言元数据。Rust 在构建时嵌入同一清单及原生目录；不建立独立手写中英选择表。测试允许注入清单和目录。

前端目录拆为 `desktop-ui/locales/zh.json` 与 `en.json`，保留 `t()` 接口；后端固定消息和原生消息分别按语言维护，既有 Markdown 提示词保留文件结构，由通用加载器按资源标识选取。不同域无需拥有相同 key 集，但每个域内各正式语言必须一致。无需引入前端打包器；资源随构建发布，Rust 嵌入资源的依赖路径需要在正式构建中校验。

不采用散布的枚举二选一，也不为新增语言设计插件下载系统：注册清单与资源已足够支撑当前扩展需求。日期只更换展示 Locale，不更换时间戳、时区、时间窗和存储格式。

### 2. 明确权威语言与启动恢复

Java 启动时解析一次并在运行配置中固定有效语言，其他配置热更新不得提前带入待重启的语言。auto 以系统 Locale 的基础语言查注册表，不匹配则 en；非法显式配置继续按 auto 兼容处理。

前端先准备英文加载和失败文案，再以有界请求读取后端状态及目标目录，成功后启动业务渲染。失败展示可重试状态；恢复后完整执行静态及动态初始化，避免重复绑定事件或启动多个刷新计时器。设置 HTML 的 lang 属性。英文目录不可读时可用最小内嵌英文加载/错误文案保持重试入口；业务消息回退顺序为当前语言、en、key。

原生壳在后端启动前只按 Windows 系统语言选择临时目录（zh，否则 en）；它不另行读取 TOML 或复制配置优先级。健康检查成功后，使用已验证端口和本次 token 请求 `/desktop/status` 的语言信息，受有界超时约束，在建立正常托盘和 WebView 前确认语言。读取失败报告本地化启动失败并沿既有失败关闭流程清理受管后端，不回退到不一致的正常就绪状态。第二实例尚无法取得后端语言时同样使用系统临时语言，保持单实例行为。

不增加上次语言磁盘缓存，避免多分发目录、旧配置及启动失败时的失效判断。代价是显式语言与系统语言不同时，后端就绪前错误提示可能使用系统语言；规格明确这一例外。

### 3. 错误在呈现边界本地化

桌面错误响应增量提供 `errorCode` 与 `errorParams`，保留原有 `error` 或既有消息字段和 HTTP 状态，避免替换整个响应模型。控制器将可预期校验/服务错误映射到稳定语义码，后端用同一目录生成兼容文本；前端优先按已知码翻译，未知码及旧响应采用通用本地化包裹与既有安全详情。

不通过匹配中文字符串来决定错误类型。路径、服务名和用户内容作为参数保留，不做模板递归，不扩大既有可公开详情范围。原生底层系统错误可以保留诊断信息，应用自己的标题、说明和操作提示必须本地化。实施清点应覆盖配置、文件、聊天、记忆、摘要及连接测试的面向用户错误。

### 4. 设置入口复用现有编辑事务

配置页增加语言选择及当前有效语言展示。下拉项修改当前 TOML 编辑草稿中的 `app.language`，由原保存入口提交，不额外静默保存，不覆盖其他未保存修改。当前草稿无法安全解析时禁用下拉并说明先修正 TOML，原编辑器继续可用。保存后显示需重启，受管桌面提示退出重开，浏览器使用方式提示重启后端并刷新；不自动结束当前对话或应用。

### 5. 扩展性以测试证明

按域校验正式语言 key 完整性、重复 key、占位参数集合及提示词资源存在性，构建时失败信息包含路径、语言和 key。Node 的目录测试不能只用 JSON.parse 后的对象发现重复 key，需在解析阶段保留重复检查。运行时破损资源仍走回退，校验与容错分别测试。

通过测试清单注入额外语言，验证 Java 解析与提示词选择、JS 消息及日期 Locale、Rust 原生消息选择；该夹具不加入生产目录或生产选择列表。保留参数安全、未知码兼容、启动失败恢复及保存后未重启等回归测试。

## Risks / Trade-offs

- 异步目录加载增加首屏失败路径 → 内嵌最小英文提示、有界请求、幂等重试和断线恢复测试。
- Rust 和 Java 资源打包路径漂移 → 正式构建校验清单及嵌入资源，运行中权威语言仍由后端提供。
- 原错误文本被测试或调用方依赖 → 保留字段及状态，调整仅依赖固定中文的测试，增加旧响应兼容测试。
- 英文长文案被截断 → 对配置、托盘、聊天和错误提示执行 Windows 双语视觉验收。
- 语言热更新与其他配置热更新混淆 → 验证保存值、运行值及 restartRequired，重启前所有正常界面保持旧语言。

## Migration Plan

1. 在功能分支实现注册与资源加载，保持原配置兼容，再迁移各域文案与原生入口。
2. 引入兼容错误元数据和语言选择入口，补齐验证；无需修改历史数据库或配置格式。
3. 先运行针对性 Java、Node、Rust 测试，再运行跨模块全量测试及 Windows 视觉验收；同步国际化主规格与中文操作说明后归档。
4. 若需回滚，恢复前一应用版本即可继续读取 auto/zh/en 配置，历史数据不需迁移；按仓库流程通过功能分支和 PR 交付，远端必需检查以最新提交为准。
