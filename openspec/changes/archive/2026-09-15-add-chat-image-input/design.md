## Context

动机见 proposal.md。当前 Deep Chat 适配器只取 text；聊天控制器从持久轮次重建模型输入。消息 mutation 上限为 256 KiB，SQLite transcript 与 AgentState 独立管理，并已有删除 intent 和完整轮次裁剪。此次跨越前端、存储与模型，需要设计独立图片资源生命周期。

## Goals / Non-Goals

**Goals:** 图片资源与 server-owned 用户轮次绑定；刷新、重试、历史导入与压缩不丢失或错误串联图片；在现有请求预算外使用专用有界通道。

**Non-Goals:** 后台截屏、OCR 服务、远程图片抓取、任意文件附件、图片编辑和生成。本期格式取 PNG/JPEG，不处理动画、SVG 或 HEIC；这些限制在界面和文档中明确呈现。

## Decisions

### 1. 独立上传，消息只保存引用

新增 `POST /desktop/chat/sessions/{id}/images`，每次接收一个有界二进制 body，返回服务端生成的 hex32 图片 ID、格式、大小、宽高及读取地址。新增同会话图片 GET 和未关联图片 DELETE。现有 JSON 追加增加用户消息 `imageIds`，读取返回 `images` 元数据；PUT 不允许变更关联。服务端判断图片真实格式并先读尺寸再受限解码，扩展名不作为信任依据。第一版采用 4 张、5 MiB/张、20 MiB/轮、2000 万像素/张的固定边界。

不采用把 base64 写进消息 JSON 的方案，因为它突破现有预算，污染摘要并增加历史序列化成本。上传路由需单独配置请求限制，不能抬高普通消息接口限制。上传串行处理，流式计数到上限即拒绝，不先无限读入内存。

### 2. 图片文件和 SQLite 元数据

在 memoryDir 下建立受管 chat-images 目录；随机名称，不使用原始文件名构造路径。SQLite 增量增加图片元数据和有序消息关联表。上传先临时写入、校验、原子移动，再登记未关联元数据；启动维护清理无记录临时文件。追加 user/pending 时在同一事务验证归属、数量、总大小和未关联状态并绑定。读取总是检查活跃会话与删除 intent，设置正确 MIME、nosniff，不接受路径参数。

未关联上传保留 24 小时，草稿移除可主动释放；发送失败保留已上传 ID 并复用，过期时从前端仍持有的 File 重新上传。删除采用既有 gate/intent，元数据删除前保存可恢复清理信息。相比全量 BLOB 入库，文件布局避免图片扩大常规 chat.db 读写；代价是需要文件与事务间的恢复流程。

### 3. 两种消息面共享草稿和发送链路

新增会话级图片草稿状态及共享选择/粘贴组件；不修改压缩的 Deep Chat bundle。增强面和 fallback 使用同一上传、校验及发送 orchestrator。无文字但存在图片时通过发送校验；无 active 会话先沿用创建流程。预览使用对象 URL，移除或草稿释放时 revoke。上传进度期间防止重复发送；持久化成功才清空所属草稿，已持久化后重试使用 canonical 关联。会话切换和组件降级都要带 generation 防止晚到结果覆盖。

### 4. 图片引用在模型调用边界展开

在 Agent 输入构造和历史恢复中加入结构化图片块，模型传输时由后端读取受管数据并展开成 OpenAI-compatible 图像内容。AgentState 持久化保留受管引用，避免每轮重复持久化 base64。实施第一步核实当前 AgentScope 序列化/模型适配扩展点，并以本地假服务商验证最终 HTTP body，而不是只断言对象类型。

同轮次重试、terminal 去重和取消仍沿用既有 gate。摘要与记忆提取仅使用文字及图片数量占位；上下文压缩只将图片转成明确占位或已有回答描述，不把 base64 当文字 token 估算。保留区的图片仍可再次发送，压缩后原图不自动进入后续请求。回收检查 transcript 与 AgentState 两侧引用，在压缩成功提交之后运行。

### 5. 模型能力采用实际错误反馈

自定义 OpenAI-compatible 模型没有可靠统一的视觉能力清单，因此不按模型名称猜测支持情况，也不新增人为白名单。服务商明确报告 image/multimodal 不支持时映射本地化错误，提示切换视觉模型；一般 400、鉴权或网络失败保持通用分类。禁止失败后自动去掉图片重发。

## Risks / Trade-offs

- 图片增加请求体和服务商 token 成本 → 限制数量与大小，沿用预算阻断和实际 usage 计量。
- AgentScope 可能在存储或压缩中丢失图片块 → 先核验依赖源码与线级请求；对恢复、压缩和同 turn 重试增加回归测试。
- 文件与数据库非原子提交 → 临时文件、未关联状态、删除 intent 和启动恢复覆盖每个中断点。
- JPEG/PNG 元数据可能含用户信息 → 文档说明选中图片会交给所配置模型；不在日志输出图片或 base64。
- 双历史保留时间不同 → 仅在双方都不再引用后清理；删除整个会话直接经 gate 协调清除。

## Migration Plan

1. 在功能分支实施并用可重复 SQLite schema 迁移新增表，旧消息默认图片列表为空。
2. 先验证历史库、图片上传和模型协议，再验证两种消息面的端到端流程。
3. 同步主规格和双语 README，执行针对性与完整 Maven 测试及 OpenSpec 严格校验。
4. 归档 change；交付 PR 时必须等待最新提交的必需检查（含 Windows 全量验证），按用户授权合并。
5. 回滚代码前备份 memoryDir；不破坏或删除新增图片数据，不承诺旧版本能读取新增关联。优先使用关闭新入口的前向修复保留数据。
