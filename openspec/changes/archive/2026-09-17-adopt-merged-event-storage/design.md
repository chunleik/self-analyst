## Context

动机见 proposal.md。当前 HeartbeatIngestionService 先调用 RawEventStore，再由 EventProjector 合并事件并为每次提交写入 raw_projection_sources；原始库按月分区。窗口/AFK 采集器重复上报区间起点和累计 duration，内容采集器上报当前时间和短 duration，两种输入均需支持。当前投影合并存在覆盖时长的路径，新算法必须取结束时间最大值。

本机只读样本约 41 万条心跳对应约 2.59 万条时间线事件；原始索引约 114 MiB，来源关联及索引约 65.5 MiB。该样本用于确定优先级，不作为迁移后容量保证。新库可能仍有有界重试回执和 WAL，不能宣称每次心跳完全没有写入成本。

## Goals / Non-Goals

**Goals:**
- 以合并事件为唯一在线活动事实源，消除永久逐心跳副本和来源映射。
- 保持现有事件 ID、查询语义、标题/文件隐私策略及高频变化检测。
- 使迁移、重试和故障处理可通过确定性回归测试验证。

**Non-Goals:**
- 不降低采样频率，不增加客户端预合并队列，不改用外部 ActivityWatch 服务。
- 不实现永久逐采样审计或任意历史精度重建，不引入长期 raw 兼容查询服务。
- 不把正在运行的用户数据目录用于实验，不自动删除迁移备份，不自动导入旧开发期 aw.db。
- 不顺带重构 Wiki/Agent 存储，不新增通用备份调度系统。

## Decisions

### 1. 合并写入与查询共享权威事件库

保留 events/buckets 及查询必需索引。将校验后的 heartbeat 直接交给事务性事件写入服务；合并、回执和 bucket 更新时间在同一事务完成。删除正常运行链路中的 raw append、projection pending/recovery、永久来源/coverage/checkpoint 写入。迁移完成的新库不保留这些表。

同一 bucket 写入串行化并由数据库事务保护；不要仅依赖 HTTP 层锁。规范化 JSON 做语义等价比较，字段顺序不影响判断。仅 heartbeat 合并，events 与导入的普通记录按原语义插入。

选择此方案而非内容字典压缩：字典压缩仍会永久保留每次心跳及索引，无法达到用户选择的 ActivityWatch 存储行为。

### 2. 连续性状态与时间算法

合并条件：同 bucket、同规范化 data、同连续采集会话，且 `old.start <= incoming.start <= old.end + pulsetime`；合并结束为 `max(old.end, incoming.start + incoming.duration)`。当前连续活动单独维护，不以最后插入的迟到记录替换它；直接 events/import 写入使该 bucket 的连续性缓存失效，避免越过新记录合并。

自有 watcher 增加每次启动的采集会话身份；观察到休眠、明显时钟回拨、采集失败/停顿时结束连续性，下一次从实际观察时间开始，重置累计 duration。用单调时钟识别调度停顿，用 UTC 表达事件时间。窗口/AFK 的累计上报必须同步修正，单改服务端 pulsetime 无法防止累计时长覆盖休眠。第三方缺少会话信息时只能依据传入事件和 pulsetime 判断，不宣称能够识别其未报告的中断。

保留采集原有周期；不将 duration 调大来掩盖缺失采样。对新起点早于当前区间的合法乱序输入独立保存，不回溯搜索跨状态合并；前端统计沿用既有重叠处理，不在本变更中发明新的去重规则。

### 3. 用短期回执承担重试幂等

自有客户端继续复用 sourceEventId，普通事件/批量导入使用明确的请求或会话加序号身份。回执仅保存身份、规范化请求指纹、事件 ID 和首次提交时间，默认保证 24 小时，提交和回执原子写入。重试不延长首次接收的有效期；超过窗口的离线队列不得自动重放。回执冲突拒绝，已删除事件的有效回执不得触发事件复活。

回执身份唯一约束解决并发重试，启动及周期维护清理过期回执；磁盘压力时不能提前删除仍在保证期内的回执，应背压拒绝新提交。限制请求体、批次和导入预算，回执不复制标题/文件元数据。过期回执页允许复用，以长期稳态大小而非总历史心跳数增长。导入的重试保证同样有界，文档明确这项与永久 raw 身份去重的差异。

不选择永久 sourceEventId 映射，它会重新引入此次要消除的线性增长；也不只用内存去重，否则重启后重试可能新增错误事件。

### 4. 收束原始层相关产品面

旧 raw 查询/重建路由保留认证后 `410` 的退役响应，统一使用 `RAW_STORAGE_RETIRED`；原始导出工具同步返回能力错误。去掉可点击的原始查看/重建入口，说明改用合并事件导出。普通事件来源标识保持兼容，导出元数据明确为 merged events；使用一致读快照避免活动区间延长造成分页期间结果漂移。

已成功发布的原始导出文档和生成源元数据保留；重新执行原始查询失败，不影响已有成果下载。新格式没有可从 raw 恢复全部历史的保证，events.db 不再称为随时可重建投影。

raw 目录、分区、完整性范围和 projector 配置标记退役、提示不再生效；迁移工具在旧格式阶段仍读取所需旧配置。保留通用数据目录与查询配置；磁盘压力和健康检查改为当前权威库的职责。外部 ActivityWatch 模式不进入本地迁移链路。

### 5. 首次升级采用旁路迁移，不直接 DROP 用户源库

识别当前 storage-format 标记和数据库 schema，分配新版本；未知/更高版本 fail-closed。以旧 events.db 的可见事件为迁移基线，保持 ID 和用户删除结果，不通过全量 raw 重放重建所有历史。

用户已确认补齐 runtime-storage 契约：根标记版本 1 仅作为旧布局准入，新程序接受 1 和 2；目标库已校验且切换计划已持久化后，在替换活动库之前持锁原子发布版本 2，版本 1 的旧程序因此拒绝新根。无标记数据先按原只读检查补版本 1，再进入独立迁移阶段；检查阶段不转换业务数据。原始备份和迁移状态由事件库格式标记协调恢复，根版本 2 不代表未完成的事件迁移可以跳过。

在隔离工作副本中核对 raw 与来源关联，补齐真正待处理的提交。旧数据无法区分未投影与已删除时必须停止并报告，不能猜测并恢复已删除事实。原始分区缺失/损坏或覆盖不一致时同样阻止自动迁移。副本恢复允许读取 raw，但不能写回源 raw/catalog。

构建紧凑目标，仅复制所需 buckets/events/索引及尚有效的必要重试身份；有效回执的响应事件 ID 必须指向迁移保留 ID。新库完整性检查、逐 bucket 记录数、事件 ID/data/时间/时长有序摘要、待处理提交处理结果及无禁止字段检查全部通过后，写入可恢复切换记录。同步 schema 版本和文件格式标记，明确处理 WAL，不能直接复制活跃 .db 文件遗漏 WAL 内容。

迁移登记记录源/目标版本、备份路径、校验结果和阶段，重启必须先完成恢复再开放写入。迁移成功后在线链路不再连接旧 raw。备份路径保留原目录边界的登记，允许用户配置的独立 rawRoot，不能靠假设 raw 一定在 data/events 下进行删除。

### 6. 容量收益与清理分开交付

活动库不含旧映射，因此新增长降低；旧库备份会暂时让总目录更大。状态分别报告 active/auxiliary/backup/staging，清理界面展示确认范围及预计释放空间。

显式清理只针对已成功迁移且校验登记的旧库；验证规范化路径及符号链接/重解析点，拒绝越界或与活动库重叠。外置 rawRoot 必须按其明确登记目标验证。清理中断可重试，未删除项仍显示，不把部分清理标记为全部成功。

## Risks / Trade-offs

- [合并后不能还原每次采样] → 界面、文档和导出来源明确表达；保留迁移前备份直至用户主动清理。
- [新权威库损坏不能依赖旧 raw 恢复] → 保留 SQLite 事务、完整性检查及导出/备份恢复路径，损坏时不静默建空库。
- [短期回执仍有空间和写入开销] → 不存 payload，24 小时回收并复用页；容量报告包含回执，验证稳态而非只看初次大小。
- [迁移需要临时额外空间] → 预估目标、工作副本和 WAL/安全余量，不足时失败并保留源数据。
- [旧库隐含删除和待投影状态难以区分] → 独立核对并在歧义时阻止迁移，不用重放绕过数据保留意图。
- [旧版客户端期待 raw 响应字段] → 对兼容事件端点保留可用事件 ID，raw 专属字段明确退役；端到端测试更新自有客户端。
- [迁移后旧程序误开新库] → 升级格式标记并验证旧版拒绝；若旧版无版本保护，明确禁止直接降级并提供隔离恢复说明，不能宣称自动回滚安全。

## Migration Plan

1. 实现并验证写入算法和新格式，再实现旧格式离线工作副本迁移；用合成/脱敏 fixture 验证，不接触真实运行目录。
2. 启动时在采集之前取得现有独占锁，执行预检、复制、待处理核对、生成、验证、持久切换和恢复状态机。
3. 切换前先发布根格式 2；中断后新程序根据 prepared 状态恢复，旧程序拒绝。成功后启动新服务并验证普通查询/统计/导出；旧库保持备份，状态展示未释放空间。
4. 切换前或新库尚无新增提交时可恢复原文件与格式标记；新库有新提交后禁止直接恢复旧快照，必须保全新库并经过显式恢复流程。
5. 用户另行执行确认清理后释放旧备份；清理后不再提供旧格式回退或逐心跳恢复承诺。

## Validation

采用固定时钟、固定数据和临时目录。覆盖同状态十万次心跳、A/B/A、边界、乱序、并发、事务失败、响应丢失、重启、休眠、导入、隐私拒绝；推进时钟超过回执窗口后验证行数及磁盘稳态。相同状态十万条 fixture 在回执过期和 WAL checkpoint 后，新库总量目标不超过旧双层基线的 20%，并报告事件/回执/索引/WAL 明细；该门槛仅适用于固定重复样本，不向真实混合数据承诺同等比例。

迁移每个阶段注入中断并检查源文件未被改写、格式一致、可查询事件不变、不会复活已删除数据；对磁盘不足、未知格式、缺失 raw、损坏源库、外置路径及越界清理单独测试。跨模块最终运行 `mvn test` 和 OpenSpec 严格校验，UI 变更保留截图。交付时同步主规格，保留旧 SPEC-RAW ID 的退役追溯说明，不复用编号。
