## Context

动机见 proposal.md。标题捕获与 heartbeat 使用不同线程；现有 generation 检查阻止隐私排除之前启动的查询在恢复后发布。前台暂时不可用也必须清除旧快照，但不能复用会丢弃待重试请求的隐私处理路径。

## Goals / Non-Goals

**Goals:** 将快照新鲜度与投递连续性分离，同时保留采集排除优先级及异步查询保护。

**Non-Goals:** 不改投递重试上限、超过 10 秒断会话及一天过期规则，不改窗口/AFK 采集器、AQL 或服务端合并策略。

## Decisions

- 抽出只递增 generation 并清空快照的失效操作；完整丢弃操作在其基础上重置投递状态。仅赋 null 无法阻止跨越暂时不可用状态的在途查询复活，因此仍需 generation。
- 在捕获轮询、UIA 完成后的前台确认、心跳轮询及真正投递前复查中，分别处理明确排除与前台不可用；排除应用或排除 pending 的判断保持优先。空快照与零句柄行为相同。
- 保留允许应用的原 pending body，不重建时间戳、身份或 data；没有真正投递的轮次不计为失败重试。后续请求仍交由既有投递组件处理超时及失败边界。
- 使用可编程前台测试替身与同步回调控制竞态，无需 Windows UIA、网络或 sleep，覆盖发送前两次前台读取之间变化、UIA 在途暂停后恢复，以及心跳已复制旧快照时 UIA 完成确认观察到前台不可用的交错。

## Risks / Trade-offs

- [保留 pending 可能误补发后来被排除的应用] → 保留现有 pending 排除复查，并增加暂停期间更新排除列表的测试。
- [只清快照可能被在途查询覆盖] → 使用 generation 失效并覆盖恢复到同一窗口的竞态。
- [把短暂恢复理解为任何时长均连续] → 明确沿用投递组件的时间和失败断会话规则，不扩大连续性窗口。

## Migration Plan

无数据或配置迁移。按功能分支提交草稿 PR 并验证 CI；不合并、不发版、不本地打包。回退可还原该提交。
